v0.3.3.2: image-gen efficiency point release (#63 + #62)

Two cost-side fixes informed by the v0.3.3 ship-validation smoke
(2026-05-03). Both bundle as a single point release so the v0.3.4
multi-project gate (task #50) starts from a tighter baseline.

#63 — stage_image_gen reuses cached request.json on retry

Symptom on the v0.3.3 smoke: a single slide's image-gen path was
attempted three times. Each attempt re-invoked ai_image_prompt.v1
LLM at ~$0.14, even though the cached <slide_id>_request.json from
the prior run was perfectly valid. Total burn ~$0.28 in cached LLM
work that should have been $0.

Fix:
- New `image_gen_approval.can_reuse_cached_request(request_path,
  expected_slide_id, expected_style=None)` helper. Returns
  (reusable: bool, reason: str). True when:
    1. Cached request exists on disk
    2. slide_id_target verifier passes (cheap: JSON parse + field check)
    3. Cached `style` matches `--image-style` override if any was set
  Otherwise False with a reason string the orchestrator logs.

- New `image_gen_approval.py check-reuse` CLI subcommand for bash
  dispatch. Exits 0 when reusable, 1 when not. Reason printed to
  stderr.

- `presentation_maker.sh::stage_image_gen` calls check-reuse before
  invoke_claude_with_retry. Reusable → skips the LLM call entirely.
  Not reusable → fresh authoring as before. Either way, the
  trust-but-verify slide_id_target check still runs after.

- 12 new unit tests on can_reuse_cached_request covering: no file,
  valid no-style-check, slide_id mismatch, style match/mismatch,
  empty expected_style skip, malformed JSON, wrong schema, plus
  4 CLI subcommand exit-code tests.

Edge cases:
- User changes --image-style mid-iteration → cached style mismatch
  → fresh authoring with the new style (correct behavior).
- User changes --tier or --mode → not currently checked by reuse
  logic. Acceptable for v0.3.3.x because: (a) the cached request's
  style/aspect/composition reflects tier+mode at original generation;
  (b) full re-author is one --image-style flag away. Track in
  v0.3.x backlog if real users hit this.

#62 — image_client worst-case preflight recalibrated

Symptom on the v0.3.3 smoke: --max-image-cost-usd 0.05 (5x the
calibrated mean of $0.014) was rejected by the preflight with
"image-gen worst-case $0.404 > remaining budget $0.050". The
$0.404 bound came from 32K output tokens × $12/M, which is the
absolute worst-case at the model's max output and 30× the calibrated
mean. Forced users to set --max-image-cost-usd 0.50 just to clear
preflight on a single $0.014 image.

Fix:
- New `_WORST_CASE_COST_USD = 0.05` constant in image_client.py.
  Calibrated as ~3.7× the v0.3.0 mean ($0.014/image, σ small from
  13 trials). Rate-card drift headroom: ~3x.
- Preflight branch now reads the constant directly instead of
  recomputing 32K-output × rate.
- BudgetExceeded message extended to mention the calibrated mean
  ($0.014/image) so users know what to expect when they hit the
  rejection.

- 3 new unit tests on the preflight: pin the constant in [$0.03,
  $0.10] band, confirm preflight clears at orchestrator default
  ($0.50) and a sane lower bound ($0.10), confirm borderline
  budget == worst-case is NOT exceeded (uses >, not ≥).

- 1 existing test extended to assert the calibrated-mean hint
  appears in the BudgetExceeded message.

Recalibration trigger documented in the constant's docstring:
re-run image_gen_calibration.py if the model id or rate card
changes, then update both the constant and the band-test.

Backwards compatibility

- v0.3.3 callers that set --max-image-cost-usd >= 0.05 see no
  behavior change.
- v0.3.3 callers that set --max-image-cost-usd 0.04 or below
  still hit BudgetExceeded — unchanged.
- v0.3.3 default --max-image-cost-usd 0.50 is now ~10x the
  worst-case (was ~1.2x). Could tighten to 0.20 in v0.3.4 once
  multi-project smoke confirms the calibrated mean holds.
- Cached request reuse is purely additive: pre-v0.3.3.2 caches
  are valid (same image-request.v1 schema, same slide_id_target
  field).

Tests: 648 → 663 passed (15 new), 1 skipped (live adversarial
integration), no regressions.
