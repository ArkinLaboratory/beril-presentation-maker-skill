v0.3.4.3: CONTRACT.md cross-skill interop pinning

Closes the v0.3.4 hub-readiness audit's "no CONTRACT.md" gap.
Single canonical document at repo root pinning the cross-skill
interop surface — every schema presentation-maker emits that other
skills might read, every schema we read from sibling skills
(adversarial, paper-writer), the CLI guarantees, the versioning
policy.

Docs-only release. Zero code changes. Tests still 726/726 passing.

Sections (8 + appendix)

1. **Purpose & scope** — what this contract pins, what it doesn't,
   when it changes (in the same commit as the producer-side change
   it documents, per feedback_cross_skill_contract_drift.md).

   - slide_spec.v1 — pointer to slide_spec.py LAYOUTS + 16-layout

   - image-request.v1 — ai_image_prompt.v1 schema, 7-style enum

   - image_provenance — append-only, quant_content_score=null in v1.
   - stage-metadata.v1 + run-summary.v1 (NEW v0.3.4.2) — full schema
     + bash trap-EXIT hook semantics.
   - 4-zone draft layout — top-level invariant, manual-edit hash
     guard contract, v0.3.0 non-migratability.

**Appendix:** contract-version table — every schema/path/version

Why this matters

The recurring cross-skill drift pattern (4 strikes documented in
feedback_cross_skill_contract_drift.md) is a producer-pretending-
nothing-changed-mattered failure mode. CONTRACT.md is the
producer-side canonical pin: when adding a layout to slide_spec,
or renaming a class in v3, or adding a stage to --resume-from, the
contract update is the producer's commit-time obligation.

It's also load-bearing for v1.0 candidacy. Without CONTRACT.md, a
hub user encountering an interop failure has no document to read
that explains "what does presentation-maker actually promise other
skills." With CONTRACT.md, the answer is a single grep away.
